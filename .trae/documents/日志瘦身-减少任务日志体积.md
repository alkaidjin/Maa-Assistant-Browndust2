# 减少 MaaBD2 任务日志体积 — 实施方案

## Context（为什么做 / 问题本质）

你上传的那份历史日志约 12MB、6.7 万行，且全英文。经查证，它的来源链路和"两个杠杆"能触及的范围如下：

- 你看到的"任务历史日志"是**第三方启动器 AUTO-MAS** 生成的：其 `config/ScriptConfig.json` 把 BD2 通用脚本的 `LogPath` 指到 `F:/MABd2v26.09.5/debug/maafw.log`，`app/task/general/AutoProxy.py` 用 `start_monitor_file()` 实时把该文件内容存成 history。
  → **history 日志 == 框架文件日志 `debug/maafw.log` 的内容**。
- `maafw.log` 由**预编译的 MaaBd2.exe + maafw/ 运行时**（MaaFramework）写出。框架 `MaaGlobalOptionEnum` 只有 `LogDir` 与 `StdoutLevel`，**没有任何文件日志级别开关**，文件日志固定全量（Trace）。
- `debug/` 实测体积：`maafw.bak.*.log` ≈ **17.7MB**、`maafw.log` 0.09MB、`go-service.log` **0.02MB**。
  → 体积大头约 **100% 在框架日志 `maafw.log`**。

因此，**你提出的两个杠杆都打不到大头**：

| 杠杆 | 有效对象 | 对 history / maafw.log 的影响 |
|---|---|---|
| ① `stdout_level` 2→3 | 仅控制台 stdout | **零影响** |
| ② 删代码里的 `log.Info` | 项目自有的 `go-service.log`、agent 输出（合计约 20KB） | **零影响** |

> 关于杠杆①：枚举为 `Off=0,Fatal=1,Error=2,Warn=3,Info=4,Debug=5,Trace=6,All=7`，**`2` 其实是 Error（默认值），不是你以为的 Debug；`3`=Warn**。而且它只作用于控制台。改它既缩小不了文件、又没有实际收益。

**结论**：项目侧能真正优化的只有"自有代码的日志"（约 20KB 级），框架 `maafw.log` / AUTO-MAS history 的体积**无法靠项目代码或配置缩小**（上游框架设计所限，二进制不可改）。

---

## 方案

### 一、项目自有日志瘦身（对应杠杆②，零风险；预期收益约 20KB）
| 位置 | 改动 |
|---|---|
| `data/maintainer/agent/go-service/logger.go:60` | `zerolog.SetGlobalLevel(zerolog.DebugLevel)` → `InfoLevel`。控制台已限定 Error+（L42-49），文件写全部；降到 Info 后一批 Debug 行（如 `taskersink/aspectratio/checker.go` 内的多处）不再落盘 |
| `data/maintainer/agent/trader/sell.go` | 删除网格滚动过程的逐次诊断行 **L385 / L388 / L396 / L399**（每滑一格就打一行），保留结果行 |
| `data/maintainer/agent/fishing/fishing.go` | 删除逐次点击行 **L416**（一轮钓鱼小游戏几十行），保留汇总行（L124）与异常路径（L288/L318/L326） |
| 其余 | `agent.go`、`main.go`、`pretask/gamesetting/gamesetting.go`、`rock-picker/main.go` 等均为一次性启动/生命周期日志，**保留** |

### 二、杠杆① 的处置
- **保持 `config/maa_option.json` 的 `stdout_level:2` 不变**（改 3 反而变 Warn 更吵，且对文件无益）；`DebugMode` 保持 false。
- 不改 `logging:false`：那会停掉文件日志，但 AUTO-MAS 靠 `maafw.log` 里的 `Close log` 判定成功（`ScriptConfig.json` 的 `SuccessLog`），关掉会导致**永远判不出成功、history 变空**。

### 三、磁盘层（可选；唯一能真正减少"落盘体积"，但对已保存的 history 无效）
> history 是运行期实时抓取的，项目侧改动**无法缩小已经保存的那份 history**；下列只能降低 `debug/` 目录的长期占用。
- `data/maintainer/tools/compact_log.ps1` 三处过期：
  - L66 `$Root` 只退 2 级 → 现指向 `data\`，应退 **3 级**到项目根（同目录 `apply_icon.ps1` 的做法）；
  - L353 写死 `@('maa.log','maa.bak.log')`，实际文件名是 `maafw.log` / `maafw.bak.<时间戳>.log`，应改用通配 `maafw.bak.*.log`；
  - L138 进程名 `mxu` 已过时（现为 `MaaBd2.exe`）。
- `data/maintainer/tools/clean_logs.ps1`：L29 同样的 Root 退级 bug，现指向不存在的 `data\debug`，**静默不删任何文件**。
- 注意：这两个脚本的调用方 `BD2MAA-Maintainer.ps1` / `Updater.ps1` **已退役**（见 `data/maintainer/README.md` L35-48），当前**无人调用**，修好后需手动跑或重新挂 hook。

## 验证
1. 改动前后各跑一轮"钓鱼 + 跑商"，对比 `debug/go-service.log` 的体积/行数（现 21KB）。
2. `powershell -File data/maintainer/tools/compact_log.ps1 -DryRun`：修好后应能报告 `maafw.bak.*` 压缩率（预期 >90%）。
3. `powershell -File data/maintainer/tools/clean_logs.ps1 -DryRun -Days 3`：应能列出 17MB 级 bak 文件。
4. 回归：跑一轮后 `debug/maafw.bak.<新时间戳>.log` 仍约 15–18MB（反证 `stdout_level` 无效），且 `maafw.log` 仍含 `Close log`（AUTO-MAS 仍能判成功）。

## 涉及文件
- `data/maintainer/agent/go-service/logger.go`（改）
- `data/maintainer/agent/trader/sell.go`（改）
- `data/maintainer/agent/fishing/fishing.go`（改）
- `data/maintainer/tools/compact_log.ps1`、`data/maintainer/tools/clean_logs.ps1`（可选，修 bug）
- `config/maa_option.json`（**不改**）

## 预期收益（务必据实预期）
- 一、二节：`go-service.log` 由约 20KB 进一步下降，agent 输出更干净，**history 体积几乎不变**。
- 三节：`debug/` 目录的长期占用可控（可压到 ~4%），**但无法缩小已保存的 history 文件**。
- 若目标是"让 AUTO-MAS 保存的 history 本身变小"，**项目侧无解**，需在上游框架或 AUTO-MAS 侧想办法。
