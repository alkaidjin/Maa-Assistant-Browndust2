# 参考：分辨率守护判定逻辑与安全分辨率白名单

> 对应优化项第 14 点。本文只**梳理与记录**，不改变任何判定语义。
> 判定代码：[`data/maintainer/agent/go-service/taskersink/aspectratio/checker.go`](../agent/go-service/taskersink/aspectratio/checker.go)
> （裁剪 fork 自 MaaEnd `64fac11`，2026-10-02 逐行核对）。

## 1. 守护是什么

go-service 启动时自动挂载 `aspectratio` tasker sink。**每次任务开始**
（`OnTaskerTask / EventStatusStarting`）它向控制器要一次当前分辨率，
不符合要求就渲染 HTML 警告页并 `tasker.PostStop()` —— 任务根本不会跑，
界面表现是"点开始立刻被停掉、弹出分辨率提示"。

`interface.json` 另有 `screencap_target_short_side: 720`：截图统一按短边 720 缩放，
所以 pipeline 坐标全部以 **1280×720 设计空间**书写，守护的目的就是保证缩放不产生亚像素畸变。

## 2. Win32 控制器（本项目唯一使用的控制器）判定规则

三个条件**同时满足**才放行，源码 `isNonADBResolutionOK()`：

| # | 条件 | 数学表达 | 实际窗口 |
|---|---|---|---|
| ① | 比例近似 16:9 | `\|w/h − 16/9\| ≤ (16/9) × 2%`，即 w/h ∈ **[1.74222, 1.81333]** | 看起来很宽（±2%） |
| ② | 不小于基准 | 长边 ≥ 1280 **且** 短边 ≥ 720 | — |
| ③ | 缩放后恰好 1280×720 | `round(720 × w/h) == 1280`，即 w/h ∈ **[1.77708, 1.77847)** | 实际约 ±0.04% |

③ 的窗口远窄于 ①：**真正起决定作用的是 ③**。它要求短边缩到 720 后长边四舍五入
正好等于 1280，差 1px 都不行（源码注释原话：1360×768 缩放后是 1275×720 会识别异常）。
因此①的 ±2% 在真实显示模式下几乎没有放行作用，判定**实际等价于"精确 16:9 整数比"**；
在 720p–4K 整数格点上理论存在 2723 个借容差通过的非标准巧合分辨率，现实硬件没有这种输出模式。

横屏竖屏都按"长边/短边"归一化比较（9:16 也能过），但棕 2 是横屏游戏，竖屏无实际意义。

### 辅助机制

- **窗口未就绪重试**：读到的宽或高 ≤100px 时每秒重截一次，最多 20 次。
- **全屏自动救援（对棕 2 不触发）**：上游逻辑会读终末地注册表
  `Software\Hypergryph\Endfield` 的 `VideoFullScreen`，若为全屏就 PostMessage
  发 Alt+Enter 切窗口化，等 500ms 复测。棕 2 机器上该注册表键不存在、读取必报错，
  此分支直接 skip —— **棕 2 用户全屏不合规时不会被自动切换，只会收到警告页**。
  这是 `pretask/gamesetting` 被动保留的直接影响，属预期行为（见 go-service README 第 3 节）。

## 3. ADB 控制器（本项目不用，仅记录差异）

ADB 路径是**精确匹配** `1280×720`，无缩放、无容差（源码 `adb_exact_resolution` 分支）。
模拟器若走 ADB 控制器必须把渲染分辨率精确设成 1280×720。

## 4. 安全分辨率白名单（Win32，理论计算通过）

下列分辨率均为精确 16:9、长边 ≥1280、缩放后恰为 1280×720：

| 分辨率 | 备注 |
|---|---|
| **1920×1080** | ⭐ 游戏内设定值，唯一已实机验证的一档（README 承诺档） |
| 1280×720 | 基准档，逻辑上通过 |
| 1600×900 | 逻辑上通过（缩放后恰好 1280×720） |
| 2560×1440 | 2K，逻辑上通过 |
| 3840×2160 | 4K，逻辑上通过 |
| 1504×846 / 1536×864 / 2048×1152 / 2304×1296 / 2880×1620 | 精确 16:9 的少见档，逻辑上通过，无实机记录 |

> "逻辑上通过"只代表源码判定放行；截图链路（DXGI/PrintWindow/FramePool）在各档上的
> 实际表现**尚未实机验证**，对外口径仍以 README 的"窗口化 1920×1080"为准。

## 5. 常见被拦分辨率（即使尺寸够大）

| 分辨率 | 比例 | 死因 |
|---|---|---|
| **1366×768**（廉价笔记本/老显示器） | 1.77865 | ①②都过，③缩放得 **1281**×720，差 1px |
| 1360×768 | 1.77083 | ③缩放得 **1275**×720 |
| 1280×768 / 1280×800 / 1440×900 / 1680×1050 / 1920×1200 / 2560×1600 | 16:10 (1.6) | ①比例不符（缩放 1152 或 1200 宽） |
| 2560×1080 / 3440×1440 | 21:9 (~2.37–2.39) | ①比例不符 |
| 1024×768 / 2160×1440 / 2256×1504 / 3000×2000 | 4:3 / 3:2 / 1.5 | ①比例不符 |
| 短边 <720 的任何档位（如 1280×700） | — | ②最小尺寸不符 |

## 6. 为什么强调"不要拖窗口边框"

控制器读到的是游戏窗口**客户区**像素尺寸，不是屏幕分辨率。游戏按内设值创建的客户区
是精确 16:9（窗口标题栏/边框在客户区之外）；鼠标拖动边框后客户区变成任意整数尺寸，
几乎必然落在 1366×768 同类的"差 1px"陷阱里，于是被 ③ 拦停。
解决方式一律是：游戏内设 1920×1080 窗口化，不要拖边框；已经拖过的重新套用内设值。

## 7. 警告页与多语言

- 文案 key：`tasker.aspect_ratio_warning.*`（`requirement_ratio` /
  `full_screen_illegal` / `requirement_ratio_window_mismatch` / `requirement_exact`）
- HTML 模板：仓库根 `locales/go-service/HTML/aspect-ratio-warning.html`
- 翻译：`locales/go-service/{zh_cn,zh_tw,en_us,ja_jp,ko_kr}.json`
  （go-service 守护页 5 语言保留，与 MXU 界面仅简体中文不冲突，见根 README 语言声明）
- 调试：`debug/go-service.log` 里搜 `resolution check`，
  含 `width/height/scaled_width/scaled_height/aspect_ratio_ok/min_resolution_ok/mode` 全字段，
  用户报"分辨率被拦"时先捞这行即可定位是 ①②③ 哪一条没过。

## 8. 实机验证清单（待用户执行，本轮不做语义改动）

1. 1920×1080 窗口化正常启动任务（回归基线）；
2. 拖一次边框再开始 → 确认警告页与日志中 `scaled_width` 数值符合本文第 5 节预测；
3. （可选，愿意拓白名单时）1600×900 / 2560×1440 各跑一次截图+识别，确认无亚像素偏移后，
   再把对应档位从"逻辑通过"升级为 README 承诺档。
